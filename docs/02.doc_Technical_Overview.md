# Technical Documentation & Architecture

This document provides a technical overview of the Gascart E-commerce platform, detailing the architecture, technology stack, and core implementation details.

---

## 1. High-Level Architecture
Gascart is built as a modern, decoupled web application consisting of three main components:
- **Frontend**: A customer-facing React application.
- **Admin Dashboard**: A specialized React interface for business operations.
- **Backend API**: A Node.js/Express server handling business logic and integrations.
- **Managed Services**: Supabase (Database, Auth, Storage) and Razorpay (Payments).

---

## 2. Technology Stack

### Frontend & Admin Dashboard
- **Framework**: React 18 with Vite
- **Language**: TypeScript
- **Styling**: Tailwind CSS
- **Icons**: Lucide React
- **Animations**: Framer Motion
- **Data Fetching**: Axios / React Query
- **Routing**: React Router DOM

### Backend API
- **Runtime**: Node.js
- **Framework**: Express.js
- **Language**: TypeScript
- **Authentication**: Custom middleware integrating with Supabase Auth
- **File Handling**: Multer (memory storage)
- **PDF Generation**: PDFKit (for Invoices and RFQs)
- **Utilities**: Archiver (ZIP exports), CSV Writer (Data exports)

### Database & Infrastructure
- **Primary Database**: PostgreSQL (hosted via Supabase)
- **Authentication Service**: Supabase Auth (JWT-based)
- **Object Storage**: Supabase Storage (Buckets for product images, resumes, and vendor documents)
- **Caching/State**: Redis (via ioredis, optional configuration)
- **Payment Gateway**: Razorpay (API + Webhooks)

## 3. Core Implementation Details

### Authentication Flow
1. User logs in via the Frontend using Supabase Auth.
2. A JWT (access token) is stored in the browser (local storage or cookies).
3. Every request to protected API endpoints includes the token in the `Authorization: Bearer <token>` header.
4. The Backend `auth.middleware.ts` validates the token against Supabase and attaches the user object to `req.user`.

### Payment Lifecycle (Razorpay)
1. **Order Creation**: Backend calls Razorpay API to create an order ID and saves it to the database with status `pending`.
2. **Verification**: After payment, the Frontend sends `razorpay_payment_id`, `razorpay_order_id`, and `razorpay_signature` to the Backend.
3. **Validation**: Backend verifies the HMAC signature using the `RAZORPAY_WEBHOOK_SECRET` to ensure data integrity.
4. **Completion**: Upon successful verification, the order status is updated to `paid` or `confirmed`.

### Search & Filtering
- Products are queried from PostgreSQL using Supabase's PostgREST or raw SQL queries in the backend.
- Full-text search and category-based filtering are handled at the database level for performance.

## 4. Project Structure (Monorepo-style)

- `/frontend`: Main e-commerce shopfront.
- `/admin-dashboard`: Internal CMS and management tool.
- `/backend`:
    - `src/controllers`: Request handling and response formatting.
    - `src/services`: Core business logic (database interactions, third-party APIs).
    - `src/routes`: API endpoint definitions.
    - `src/middlewares`: Auth, error handling, and rate limiting.
    - `src/config`: Environment configurations.
- `/docs`: Project documentation and setup guides.

---

## 5. Security Measures
- **Rate Limiting**: Implemented globally and strictly on sensitive routes (auth, logging) using `express-rate-limit`.
- **Security Headers**: Managed by `helmet` to protect against XSS, clickjacking, and other common vulnerabilities.
- **CORS**: Restricted to trusted origins (Frontend and Admin URLs) dynamically based on the environment.
- **Audit Logging**: Specific administrative actions and authentication events are logged for compliance and security monitoring.
